TL;DR

Seven task groups in one strictly serial chain, no parallelism: the domain upright rule first (the only half pnpm vitest run can verify), then the type widening behind a pnpm typecheck gate, then the plan extractions, then factory and buttons, the editor parameterisation, and the gondola drawing last. 40 steps, 4 domain tests (one assertion moved, three added), zero web tests by project decision. The spec's decomposition is confirmed on all three counts, with one correction that would otherwise ship as a silent runtime bug.

Key Decisions

  • Confirm: one ShelfUnitEditor parameterised on a units path prefix. The variants differ by one path segment, and a sibling would be a 363-line copy.
  • Confirm: two plan components sharing an extracted header. The gondola geometry (two strips, one selection, captions) is a different drawing, not a parameter.
  • Confirm: the six sub-components inside ShelfUnitEditor.tsx stay file-local and unexported. One editor serves both variants, so no second consumer exists. This overturns the codebase-analysis recommendation, whose premise the shared-editor decision removed.
  • Correction to the spec's parenthetical: ShelvesFields does take the units path prefix. Its useFieldArray name is a wall path. Only height and extras are genuinely untouched.
  • Extract ShelvesSummary and SCALE_PX_PER_CM alongside LayoutPlanHeader. All three acquire a real second consumer in group 6, so the extraction is not speculative.
  • The leg scope enters as a key on the context object, not as a third parameter. It keeps the (context, inventory) signature that backend/domain.md mandates.
  • Buttons and factory (group 4) land before the gondola drawing (group 6). A gondola is priced by the server on its first autosave with no plan component in existence.
  • Groups are serialised by dependency, not scheduled concurrently. Three files are each touched by two or three groups.

Open Questions / Risks

  • criticalThe two numbers in the gondola's delegated context are not the same number. The delegated numberOfLayouts keeps folding in the side count; the leg scope is the run-level count narrowed by ceil(numberOfGondolaUnits / 2). Confusing them distorts the price with no failing test, because the fixture's second entry gives the same answer either way. Step 1.3 exists only for this, and test 1.1c pins feet alongside uprights.
  • criticalA wall path inside the parameterised editor typechecks and fails at runtime. layouts.{i}.shelfUnits.{u}.shelves stays a legal Path<OfferInput> after the widening, so a missed prefix in ShelvesFields compiles, lints and writes to a key a gondola does not have. Step 5.3 checks each of the six paths by name.
  • warningTemplate literal path composition has no precedent in this repo. ${unitsPath}.shelfUnits.${unitIndex}.width must satisfy FieldPathByValue<OfferInput, number> over a two-member union. Fallback in 5.5, and it never involves a cast.
  • warningFive of the seven groups have no automated gate at all. Groups 2 to 6 are covered by pnpm validate and by nothing else until the E2E phase. No step touching the view may be reported as done on pnpm validate alone.
  • infoThe mockup's drawer heading reads „Regał 3" where the application says „Ciąg {n}". The plan keeps the application's copy and records the deviation rather than acting on it.
  • infocomponent:type-picker is deliberately uncovered. It is variant B of the add-run screen, which the spec rejects.
  • infoEvery offer re-saved after this change re-prices its gondolas. Nothing is persisted today, so there is nothing to migrate.

Dependency chain

Groups 3 and 4 are the only pair whose declared dependencies would permit concurrency, and they are still run in order because group 4's checkpoint is easier to read against an unchanged wall path. OfferLayouts.tsx (groups 2, 4, 6), WallLayoutPlan.tsx (2, 3, 5) and ShelfUnitEditor.tsx (2, 5) are each shared, so nothing here is safe to schedule concurrently even where the graph allows it.

What verifies what

Expected tests for the whole feature: 4 to 6 (4 in group 1, up to 2 more in group 7). That is far below the usual band, and it is honest rather than thin. There are zero tests under packages/apps/web, Vitest runs in a Node environment with no JSDOM (vitest.config.ts would not match a .test.tsx file), coverage is collected from packages/domain only, and .maister/docs/standards/testing/test-writing.md records that UI components have no unit tests by decision. Do not propose component tests.
