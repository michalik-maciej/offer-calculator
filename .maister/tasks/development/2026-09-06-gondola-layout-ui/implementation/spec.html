TL;DR

A gondola becomes creatable, editable, drawable and priceable, always symmetric: one gondolaUnits entry with numberOfGondolaUnits: 2. The form generic collapses to OfferInput, deleting offer.types.ts and the hydration cast with it. Uprights become shared between the sides, carried by an optional leg scope that calculateWallLayoutDemand defaults for the wall path, so no wall assertion can move. The gondola ships without an end cap, understating the standard case.

Key Decisions

  • Collapse the form type to OfferInput, delete offer.types.ts. A mixed offer makes any per-variant narrowing factually false, so two narrowed types would double a cast the coding-style standard already rules out.
  • Upright rule: ceil(numberOfGondolaUnits / 2) * (units + 1) * numberOfLayouts per entry. One shared column per pair of sides, a full column for a lone side, never a fraction.
  • calculateWallLayoutDemand keeps its leg counting and gains an optional leg scope, defaulting to numberOfLayouts. The wall path passes nothing, so its result and its list order are untouched by construction, and no new domain file is needed.
  • The gondola orchestration passes ceil(numberOfGondolaUnits / 2) * numberOfLayouts as that scope. calculateLegDemand already expresses the rule through its numberOfLayouts argument, so the shared column costs one argument rather than a refactor of the file the working wall pricing rests on.
  • The wall demand output is frozen in content and in order. Three passing tests compare whole results with toEqual, and the default keeps that promise without anyone having to preserve an order by hand.
  • Two add buttons: „Dodaj ciąg przyścienny" and „Dodaj gondolę". Binding mockup decision, and this control is the only entry point into the whole feature.
  • The gondola is drawn as two strips back to back, both from the same configuration. Binding mockup decision, it is what a gondola physically is, and it matches the v2 prior art geometry.
  • One editor parameterised on a units path prefix, two separate plan components. The editor difference is one path segment; the plan difference is what it draws.
  • The gondola factory takes its defaults from createDefaultWallLayout and builds the object key by key. No twelfth @/domain import in the browser, and no wall key can leak into a gondola.

Goal and scope

Give the user a way to add, edit, see and price a double-sided run (gondola) in the offer configurator, and correct what a gondola costs by sharing one column of uprights between its two sides, as the first version of this calculator did.

In scope
  • Two add buttons, gondola visible from the first visit
  • Default gondola factory, one entry, two sides
  • Plan drawing: two strips back to back, one configuration
  • Drawer editing applying to both sides at once
  • Shared run header for both run types
  • Shared uprights in calculateGondolaLayoutDemand
  • Form type widening to OfferInput
Out of scope (each its own task)
  • End caps (szczyt), double backs, bottom and top covers. critical The client's standard gondola has an end cap, so every quote this iteration produces for the standard case is understated. Accepted knowingly, and to be said out loud to the client before the demo.
  • The „półka nie głębsza niż baza" validation
  • Right-click menu, shelves dialog redesign, drawer ordering
  • The permanent caption at the bottom of the screen
  • Asymmetric gondolas, per-side editing, „rozłącz gondolę"
  • Converting an existing run between the two types
  • buildLayoutDescription beyond gondolaUnits[0]
  • The pre-existing defects recorded in the codebase analysis

Technical approach

The form type: collapse to OfferInput (the decision this spec owed)

offer/offer.types.ts narrows the layout union to LayoutWall[] and is the form's type argument in six other files (useForm at OfferFormProvider.tsx:18, useFormContext everywhere else). Option A is chosen: the type collapses to OfferInput and the file is deleted.

  1. Option B is not merely stylistic debt, it is false. The configurator explicitly supports an offer mixing both run types, and for such an offer neither WallOfferInput nor a new GondolaOfferInput describes the form value. Option B keeps a cast the data contradicts, in two places instead of one.
  2. It removes a live defect for free. OfferFormProvider.tsx:37 force-casts a hydrated offer to the wall type today. The coding-style standard is explicit that narrowing is done with a real guard and never with a cast.
  3. It deletes a file instead of adding one, which is what minimal-implementation asks of a change with two viable shapes.
  4. The narrowing it forces is needed anyway. R3 already requires a structural guard per layout, and each plan narrows once at the top, folding into the if (!layout) return null guard already required there.
  5. Field paths widen for free. FieldPathByValue<OfferInput, number> covers the gondola paths, so the steppers need no change.

The cost is real: every whole-layout useWatch returns a union. Order of work follows from it: widen the type and run pnpm typecheck before writing any new component.

The upright rule and how it reaches calculateLegDemand 
uprights per gondolaUnits entry = ceil(numberOfGondolaUnits / 2) * (units + 1) * numberOfLayouts
feet     per gondolaUnits entry = (units + 1) * numberOfLayouts * numberOfGondolaUnits  (unchanged)
backs, base shelves, shelves    = per side, unchanged

units is the entry's summed numberOfShelfUnits; numberOfLayouts is the run-level value. For the shape this UI creates (one entry, two sides) that is one column of units + 1 per run copy; for a lone side it is a full column, which is physically right. The ceil guarantees an integer: calculateBomPrice and breakdownDemandByCategory take the demand list raw and neither rounds, so half an upright would surface in Rozpiska as "0.5".

Uprights are the only one of the five demands that now needs a scope different from the other four, and calculateWallLayoutDemand computes all five in one call. calculateWallLayoutDemand keeps that call and takes one optional leg scope, defaulting to numberOfLayouts. The wall path passes nothing and is therefore unchanged, byte for byte and element for element. The gondola orchestration keeps delegating per side and passes ceil(numberOfGondolaUnits / 2) * numberOfLayouts, which calculateLegDemand multiplies by units + 1 to give exactly the rule above.

Read the two numbers carefully, they are not the same number. The delegated context keeps folding the side count into its numberOfLayouts (numberOfLayouts * numberOfGondolaUnits), which is what keeps back panels, base shelves, shelves and feet at a full set per side. The leg scope is the run-level numberOfLayouts narrowed by ceil(numberOfGondolaUnits / 2) instead, and it applies to uprights only. Against the existing gondola fixture: entry zero (2 sides, 3 units, 1 run) gives feet (3 + 1) * 2 = 8, unchanged, and uprights (3 + 1) * 1 = 4, down from 8; entry one (1 side, 1 unit, 1 run) gives ceil(1 / 2) = 1, so both feet and uprights stay at 2.

Three reasons this beats extracting a leg-free core into a shared function:

  1. It cannot move the wall path. Legs sit in the middle of the returned list (backs, base shelves, shelves, legs, feet, extras), and calculateWallLayoutDemand.test.ts:43 freezes { id: "leg-130-8-3", quantity: 12 } as the tenth element of a whole-list toEqual. Any extraction either restores legs to the middle by hand or reorders the list; a default argument does neither.
  2. It creates no new domain file. The order-preserving extraction needs a shared leg-free function, which under backend/domain.md means a new folder, name and test, on the one path where nothing was wrong.
  3. calculateLegDemand already expresses the rule. Its numberOfLayouts argument means "how many columns of this run exist", which is exactly what the gondola narrows.

The counter-argument is that a scope argument is a coefficient passed into a shared calculation, which reads less explicitly than two orchestrations each counting their own. Accepted here because the argument is named, optional and defaulted: the wall call site says nothing at all, so the function still reads as "a full column per run copy unless the caller says otherwise". The earlier reason for rejecting this shape, that it introduces a fraction into a function working in whole numbers, is false under the rule that was chosen: ceil(n / 2) is an integer for every integer n.

Component decomposition, gondola shape, the union-ordering trap, persistence

Editor: one ShelfUnitEditor parameterised on a units path prefix (layouts.{i} for a wall, layouts.{i}.gondolaUnits.0 for a gondola), which carries depth and shelfUnits. height and extras stay at run level for both variants, so ShelvesFields and ExtrasFields are untouched apart from the generic. A sibling editor would be a copy of 363 lines differing by one path segment.

Plan: two components sharing the extracted header. The gondola plan iterates gondolaUnits.0.shelfUnits, renders the resulting strip twice, and reads depth from the gondola unit rather than from the layout. Dispatch: a hand-written branch in OfferLayouts.tsx, matching the three structural branches the domain already uses.

Shape: exactly one gondolaUnits entry with numberOfGondolaUnits: 2, pinned by the factory, never rendered and never edited. That is what removes the side index, the per-side editor and the third drawer-selection coordinate. Because there is one entry, buildLayoutDescription reading only gondolaUnits[0] is correct for everything this UI produces.

What that shape prices, and what it does not: two sides of shelf units with their back panels, base shelves, shelves, one shared column of uprights, two full sets of feet, and whatever the user adds under „Inne elementy ciągu". It carries no end cap, no double back and no bottom or top cover. The end cap is the commercially significant one: the client's standard gondola has one, so a quote produced by this iteration for the standard case is systematically low. Anything an end cap would have contributed can still be entered by hand as an extra, but nothing in the UI says so.

Union-ordering trap: OfferInputSchema lists gondola first and Valibot returns the first fully valid option while stripping unknown keys, whereas the domain switches on isLayoutWall first. An object carrying both gondolaUnits and layout-level depth / shelfUnits would persist as a gondola with its wall keys stripped, yet classify as a wall. It stays dormant as long as no path produces a hybrid, which is why the factory builds key by key and why nothing here converts a run between types.

Persistence: no schema, migration, API or Prisma change. A gondola appended into the field array is validated and priced on the first autosave, before any plan component exists, which is the natural mid-implementation checkpoint. A persisted gondola with several diverging entries gets no code written for it; the only requirement is that nothing destroys it, and React Hook Form keeps the remaining entries in the value.

Testing approach and standards

2 to 8 focused tests per implementation step group. Test verification runs the new and touched tests, not the entire suite, with pnpm vitest run as the regression gate before a step is reported. The domain half is the only part this suite can verify. Candidate assertions:

  1. A two-sided gondola entry yields one shared column of uprights (units + 1), multiplied by numberOfLayouts.
  2. A one-sided entry keeps a full column, so mixed entries add up as the rule says.
  3. No demand entry the orchestration returns carries a fractional quantity.
  4. The wall demand result is unchanged when no leg scope is passed, asserted on the whole list including order (the existing calculateWallLayoutDemand test, which must pass untouched).

Binding project constraints: nothing is mocked, ever (the domain depends on nothing and collaborators are injected); tests sit beside their subject as {name}.test.ts; each file opens with an explicit import { describe, expect, it } from "vitest" and holds a single top-level describe with it; fixtures come from packages/domain/src/fixtures; assertions compare the whole result with toEqual.

criticalThe React layer cannot be unit-tested here. Zero tests under packages/apps/web, Vitest in Node with no JSDOM (the config would not even match a .test.tsx file), coverage from packages/domain only. This is a recorded decision, not an accident: testing/test-writing.md states that UI components have no unit tests by decision. Do not propose or write component tests, and do not propose lifting the constraint inside this task.

Browser verification is what stands in for those tests, and it is the only real gate for the view layer (analysis/requirements.md names the E2E phase as „jedyną realną bramką dla warstwy widoku"). It is not optional manual clicking: the E2E phase runs the script in Success Criteria 1 to 5 against a running application and leaves evidence.

Success criteria

Criteria 1 to 5 are the E2E script for the view layer, which has no unit tests by decision. Criteria 6 to 8 are mechanical and run from the command line.

  1. „Dodaj gondolę" produces a run whose plan shows two strips of identical boxes, „Strona 1" above and „Strona 2" below.
  2. Editing depth, height, width, unit count or shelves changes both strips at once, and after the autosave the header shows a description beginning „1 x ciąg regałów dwustronnych" and a price.
  3. Reloading the offer brings the gondola back unchanged, with no cast in the hydration path.
  4. Rozpiska shows no fractional quantity for any gondola, and the uprights line for a default gondola with N units reads N + 1 per run copy, not 2 * (N + 1).
  5. An offer mixing a wall run and a gondola prices both, and the wall run's price is identical to what it was before.
  6. pnpm validate and pnpm vitest run pass, and the only changed assertion in the whole suite is the gondola upright quantity, 8 to 4 in calculateGondolaLayoutDemand.test.ts. Nothing else moves, including list order.
  7. offer.types.ts no longer exists and no as WallOfferInput cast remains.
  8. grep -rn 'from "@/domain' packages/apps/web/src still returns the same eleven lines.

Known limitations

  • A gondola header's description is built from gondolaUnits[0]: correct for everything this UI creates, incomplete for a run that arrives with several entries by another route.
  • Such a run draws only entry zero while its price covers all of them. Nothing is corrupted, but the drawing and the price disagree silently.
  • The gondola shipped here is a correct but partial answer to point 5 of the client's list: end caps, double backs and covers are deliberately deferred. Because the client's standard gondola has an end cap, the quote for the standard case is systematically low, and the only workaround in this iteration is entering the missing parts by hand under „Inne elementy ciągu". Say this to the client before the demo rather than letting the demo raise it.
  • numberOfLayouts still has no React Hook Form validation, only an HTML min attribute, so a run can be driven to zero and silently priced at nothing. Pre-existing, inherited by the shared header, out of scope here.
